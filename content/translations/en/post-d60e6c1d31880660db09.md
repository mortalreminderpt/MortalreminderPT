## CPU Utilization

Because early CPUs were extremely expensive to manufacture, people would **hope to keep the CPU working as much as possible**.

**CPU utilization**: refers to the proportion of time the CPU is busy out of the total time.

**Utilization** = device busy time / total time

Eg. A certain computer supports only single-program operation. A job initially needs to run on the CPU for 5 seconds, then use a printer to print output for 5 seconds, and then execute for another 5 seconds before it can finish.
In this process, what are the CPU utilization and printer utilization respectively?

CPU utilization:

$$
\begin{equation}
\dfrac {5+5} {5+5+5}=66.66\%
\end{equation}
$$

Printer utilization:

$$
\begin{equation}
\dfrac {5} {5+5+5}=33.33\%
\end{equation}
$$

When multiple programs execute concurrently, a **Gantt chart** is usually used to assist the calculation.

## System Throughput

For computers, it is hoped that as many jobs as possible can be processed in as little time as possible.

**System throughput**: the number of jobs completed per unit time

System throughput = total number of completed jobs / total time spent

Eg. A certain computer system finishes processing 10 jobs and spends a total of 100 seconds, so the system throughput is 10/100 = 0.1 jobs/second

## Turnaround Time

For a computer user, they care a lot about how much time their job takes from submission to completion.

**Turnaround time** refers to **the time interval from when a job is submitted to the system until the job is completed**.

It includes four parts in total:
1. The time the job waits in the backup queue in external storage for job scheduling (high-level scheduling);
2. The time the process waits in the ready queue for process scheduling (low-level scheduling, ready state);
3. The time the process executes on the CPU (running state);
4. The time the process waits for I/O operations to complete (blocked state).

The latter three items may occur multiple times during the entire processing of a job.

(Job) **turnaround time** = job completion time - job submission time

### Turnaround Time, Average Turnaround Time

For users, they care more about the turnaround time of their own individual jobs;
but for the operating system, it cares more about the overall performance of the system, so it cares more about the average of the turnaround times of all jobs, that is, the average turnaround time.

**Average turnaround time** = sum of turnaround times of all jobs / number of jobs

Some jobs have short running times, and some jobs have long running times. Therefore, when the turnaround time is the same, jobs with different running times definitely give users different feelings.

### Weighted Turnaround Time, Average Weighted Turnaround Time

**Weighted turnaround time** = job turnaround time / job actual running time = (job completion time - job submission time) / job actual running time

For two jobs with the same turnaround time, the job with the longer actual running time is served for more time within the same period, so its weighted turnaround time is smaller and user satisfaction is higher.

For two jobs with the same actual running time, the one with the shorter turnaround time has a smaller weighted turnaround time and higher user satisfaction.

Note:
- Weighted turnaround time must be ≥ 1;
- Both weighted turnaround time and turnaround time are better when smaller.

**Average weighted turnaround time** = sum of weighted turnaround times of all jobs / number of jobs

## Waiting Time

Computer users hope that their jobs wait for the processor as little as possible.

**Waiting time** refers to the **sum of time a process/job is in the state of waiting for the processor**. The longer the waiting time, the lower the user satisfaction.

After a job is submitted, it first enters the job backup queue (in external storage), and in the backup queue it **waits to be served (scheduled)**.

After the job is loaded into memory, **the corresponding process is created**. This process will be served by the CPU and by I/O devices, and of course there will also be times when it is **waiting to be served**.

For a **process**, waiting time refers to the **sum of time spent waiting to be served** after the process is created.
During the period of waiting for I/O to complete, the process is actually also being served, so it is not counted in the waiting time.

For a **job**, not only the **waiting time after the process is created** must be considered, but also **the time the job waits in the backup queue in external storage** must be added.

How long a job needs to be served by the CPU and by I/O devices in total is generally fixed and unchanging, so scheduling algorithms actually only affect the waiting time of jobs/processes.
Of course, similar to the previous metrics, there is also **average waiting time** to evaluate overall performance.

## Response Time

For computer users, they hope that the requests they submit (for example, entering a debugging command via the keyboard) start being served and responded to by the system as early as possible.

**Response time** refers to the time from when the user **submits a request** to when **the first response is produced**.
