## Intent
**Separate the construction of a complex object from its representation** so that **the same construction process can create different representations**

## Motivation
An RTF reader should be able to convert RTF into a variety of text formats.
The reader can convert an RTF document into ASCII text or into a text window component that can be edited interactively.
However, the number of possible conversions is unlimited, so it should be easy to add new conversions without changing the RTF reader.

One solution is to configure the RTFReader class with a TextConverter object that can convert RTF into another text representation.
When RTFReader parses an RTF document, it uses TextConverter to perform the conversion.
Whenever RTFReader recognizes an RTF token (either plain text or an RTF control word), it sends a request to TextConverter to convert that token.
The TextConverter object is responsible for performing the data conversion and representing the token in a specific format, as shown in the figure



Subclasses of TextConverter handle different conversions and different formats specially.
Each converter class hides the mechanism for creating and assembling a complex object behind an abstract interface.
The converter is independent of the reader, and the reader is responsible for parsing an RTF document.

The Builder pattern describes all these relationships. Each **converter class is called a Builder in this pattern, and the reader is called a Director**.
In the example above, the Builder pattern separates the algorithm for parsing a text format (that is, the parser for an RTF document) from the algorithm that describes how to create and represent a converted format.
In this way, we can reuse the parsing algorithm of RTFReader to create different text representations from an RTF document—simply configure RTFReader with a different TextConverter subclass.

## Applicability
- When the algorithm for **creating** a complex object should be **independent of the parts that make up the object and how they are assembled**;
- When the construction process must allow **the object being constructed to have different representations**.

## Structure

## Participants
1. Builder (TextConverter)
- Specifies an abstract interface for creating each part of a Product object

2. ConcreteBuilder (ASCIIConverter, TeXConverter, TextWidgetConverter)
- Implements the Builder interface to construct and assemble the parts of the product;
- Defines and keeps track of the representation it creates;
- Provides an interface for retrieving the product (for example, GetASCIIText, GetTextWidget)

3. Director (RTFReader)
- Constructs an object using the Builder interface

4. Product (ASCIIText, TeXText, TextWidget)
- Represents the complex object being constructed. ConcreteBuilder creates the internal representation of the product and defines its assembly process;
- Contains the classes that define the constituent parts, including the interface for assembling these parts into the final product.

## Collaborations
- The user creates a Director object and configures it with the desired Builder object;
- Once the product parts are generated, the Director notifies the Builder;
- The Builder handles the Director's requests and adds parts to the product.
- The user retrieves the product from the Builder.
