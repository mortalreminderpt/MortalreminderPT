## Redux Design Philosophy

As JavaScript single-page application development grows increasingly complex, our code has to manage more state than ever before. This state may include server responses, cached data, data generated locally that has not yet been persisted to the server, and also UI state such as the active route, the selected tab, whether to show a loading animation or a paginator, and so on.

Managing constantly changing state is very difficult. If a change in one model causes a change in another model, then when the view changes, it may cause a change in the corresponding model as well as in another model, and this change in turn may cause a change in yet another view. Once these chain reactions reach a certain point, you have no idea what actually happened. When state changes, why it changes, and how it changes are no longer under control. When the system becomes intricate and complex, reproducing problems or adding new features becomes extremely difficult.

If the above is not bad enough, consider the new requirements that are becoming increasingly common in the field of front-end development. As front-end developers, we may need to optimize updates, do server-side rendering, fetch data before a route change, and so on. We have to take charge of complex work unlike anything before, and it is inevitable to ask: is it time to give up? The answer, of course, is no.

Complexity is hard to reduce because we always conflate two concepts that are difficult for us to understand: Mutation and asynchrony. I compare them to Mentos and cola. Separately, both are excellent, but mixed together they are a mess. Some libraries, such as React, try to solve this problem at the view level by prohibiting asynchronous operations and direct DOM manipulation. But the fly in the ointment is that React leaves state management to the developers themselves, and this is where Redux comes in.

Following in the footsteps of Flux, CQRS, and Event Sourcing, Redux attempts to make state changes predictable by restricting when and how updates occur. These restrictions are embodied in the three principles of Redux:

- **Single source of truth**: The entire state of the application is stored in a single object tree, which makes it easy to manage and debug.
- **State is read-only**: The only way to change state is to dispatch an action, which ensures the predictability of state.
- **Use pure functions**: Pure functions (reducers) are used to describe how state changes in response to actions, making the state change process transparent and easy to test.

Redux's design is partly inspired by the Flux architecture and the architectural pattern of the Elm programming language, but through simplification and optimization it makes state management more intuitive and efficient. Since its release, Redux has become a widely used state management library in front-end development and has a large community and a rich ecosystem of support.

## Single Source of Truth

> The global state of the entire application is stored in a single object tree, and this object tree exists in only one store.

This principle simplifies the development of isomorphic applications, because the state on the server can be serialized and injected into the client without doing anything else. A single-source-of-truth state tree also simplifies debugging and monitoring of the application; it also lets you persist application data locally during development, thereby accelerating the development cycle. In addition, some features that were previously difficult to implement, such as "undo/redo", become very easy to implement with Redux under the single source of truth principle.

```js
console.log(store.getState())
/* 输出
{
  visibilityFilter: 'SHOW_ALL',
  todos: [
    {
      text: 'Consider using Redux',
      completed: true,
    },
    {
      text: 'Keep all state in a single tree',
      completed: false
    }
  ]
}
*/
```

## State Is Read-Only

> The only way to change state is to dispatch an action, and an action is a plain object used to describe an event that has occurred.

This principle ensures that neither view behavior nor network request callbacks can directly modify state; instead, they can only express the intent to modify state. Because all modifications are centralized and executed strictly one after another in order, there is no need to worry about race conditions. Actions are just plain objects, so they can be logged, serialized, stored, and replayed later during debugging or testing.

```js
store.dispatch({
  type: 'COMPLETE_TODO',
  index: 1
})

store.dispatch({
  type: 'SET_VISIBILITY_FILTER',
  filter: 'SHOW_COMPLETED'
})
```

## Use Pure Functions to Perform Modifications

> To describe how actions change the state tree, you need to write pure reducers.

A reducer is a pure function that receives the previous state and an action and returns the new state. Remember, you must return a new object rather than modifying the previous state. You can start with just a single reducer, but as the application grows in complexity, you can split large reducers into smaller reducers that each manage different parts of the state tree. Because reducers are just functions, you can control the order in which they are called, pass in additional data, and even write reusable reducers to handle common tasks such as a paginator.

```js
function visibilityFilter(state = 'SHOW_ALL', action) {
  switch (action.type) {
    case 'SET_VISIBILITY_FILTER':
      return action.filter
    default:
      return state
  }
}

function todos(state = [], action) {
  switch (action.type) {
    case 'ADD_TODO':
      return [
        ...state,
        {
          text: action.text,
          completed: false
        }
      ]
    case 'COMPLETE_TODO':
      return state.map((todo, index) => {
        if (index === action.index) {
          return Object.assign({}, todo, {
            completed: true
          })
        }
        return todo
      })
    default:
      return state
  }
}

import { combineReducers, createStore } from 'redux'
const reducer = combineReducers({ visibilityFilter, todos })
const store = createStore(reducer)
```
