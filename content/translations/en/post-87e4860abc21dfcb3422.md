## Intent
Provide an **interface** for creating **a series of related or interdependent objects** without specifying their concrete classes

## Motivation
When designing a GUI that supports different themes, a GUI under the same theme will include components such as scroll bars, windows, and buttons.
To ensure the portability of themes, an application should not hard-code components for a specific theme; otherwise, changing the theme becomes difficult.

Therefore, an abstract WidgetFactory class can be defined, declaring the interface used to create basic window components.
Among them, each window component has an abstract class, and their subclasses implement the concrete theme of the window component.
Users obtain window components through the interface provided by WidgetFactory, but users do not know the concrete classes they use, so users do not depend on a specific theme.

Each theme corresponds to a concrete WidgetFactory subclass, and each subclass implements the component operations used to create that theme.
**Clients interact only with the interface defined by the abstract classes, and do not use the interfaces of specific classes**

## Applicability

- A **system** should be **independent of how its products** are created, composed, and represented;
- A **system** should be configured with **one of multiple product families**;
- The **design of a series of related product objects** should be emphasized for **joint use**;
- Provide a **product class library**, but only **expose their interfaces** rather than their implementations.

## Structure

## Participants

1. AbstractFactory (WidgetFactory)
- Declares an operation interface for creating abstract product objects

2. ConcreteFactory (MotifWidgetFactory, PMWidgetFactory)
- Implements the operations for creating concrete product objects

3. AbstractProduct (Window, ScrollBar)
- Declares an interface for a class of product objects

4. ConcreteProduct (MotifWindow, MotifScrollBar)
- Defines a product object to be created by the concrete factory;
- Implements the AbstractProduct interface

5. Client
- Uses only the interfaces declared by the AbstractFactory and AbstractProduct classes

## Collaborations

- Usually, an instance of a ConcreteFactory is created at runtime, and this concrete factory creates product objects with specific implementations. To create different product objects, clients should use different concrete factories;
- AbstractProduct defers the creation of product objects to its ConcreteFactory subclasses

## Consequences

1. **It isolates concrete classes**: It separates clients from class implementations, and clients manipulate instances through their abstract interfaces.
Product class names are also isolated in the implementation of the concrete factory, that is, they do not appear in the client's code.
2. **It makes exchanging product families easy**: A concrete factory class appears only once in an application, namely when it is initialized, which makes changing a ConcreteFactory easy.
Different product configurations can be used simply by changing the concrete factory, because an abstract factory creates a complete product family, so the entire product family changes immediately.
3. **It promotes consistency among products**: When product objects in a family are designed to work together, an application can use only objects from the same family, and AbstractFactory makes this easy to achieve
4. **Supporting new kinds of products is difficult**: Because AbstractFactory determines the set of AbstractProducts.
Therefore, supporting a new kind of Product requires extending the factory's interface and extending all of its ConcreteFactories
