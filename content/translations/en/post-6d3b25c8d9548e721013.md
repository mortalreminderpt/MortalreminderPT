## Why introduce monitors
Problems with the semaphore mechanism: writing programs is difficult and error-prone.

Could we design a mechanism that lets programmers write programs without having to worry about complex PV operations, making coding easier?

In 1973, Brinch Hansen first introduced the "monitor" construct into a programming language (Pascal)—a high-level synchronization mechanism.

## Definition and basic characteristics of monitors
A monitor is a special software module composed of these parts:
1. A description of the **shared data structures** local to the monitor;
2. A **set of procedures** that operate on these data structures;
3. Statements that set initial values for the shared data local to the monitor;
4. A monitor has a name.

Basic characteristics of monitors:
1. Data local to the monitor can only be accessed by procedures local to the monitor;
2. A process can enter the monitor to access shared data only by calling a procedure within the monitor;
3. **Only one process at a time is allowed to execute an internal procedure within the monitor**.

## Using monitors to solve the producer-consumer problem

Monitor:
```c
monitor ProducerConsumer
    condition full, empty;      // 条件变量用来实现同步（排队），管程中设置条件变量和等待/唤醒操作，以解决同步问题
    int count = 0;              // 缓冲区中的产品数
    void insert(Item item) {    // 把产品item放入缓冲区，由编译器负责实现各进程互斥地进入管程中的过程
        if(count == N)
            wait(full);
        count++;
        insert_item(item);
        if(count == 1)
            signal(empty);
    }
    Item remove() {             // 从缓冲区中取出一个产品
        if(count == 0)
            wait(empty);
        count--;
        if(count == N-1)
            signal(full);
        return remove_item();
    }
end monitor    
```

Usage example:
```c 
/* 生产者进程 */
Producer() {
    while(1) {
        item = 生产一个产品;
        ProducerConsumer.insert(item);
    }
}

/* 消费者进程 */
Consumer() {
    while(1) {
        item = ProducerConsumer.remove();
        消费产品item;
    }
}
```

The purpose of introducing monitors is to implement process mutual exclusion and synchronization more conveniently:
1. **Shared data must be defined in the monitor** (such as the buffer in the producer-consumer problem);
2. **"Entry points" for accessing these shared data must be defined in the monitor**—in fact, these are just some functions (for example, in the producer-consumer problem, one function can be defined to put products into the buffer, and another function can be defined to take products out of the buffer);
3. **Shared data can only be accessed through these specific "entry points"**;
4. A monitor has many "entry points", but **only one of them can be open at a time**, and **only one process or thread can be allowed to enter** (for example, in the producer-consumer problem, each process needs mutually exclusive access to the shared buffer. This characteristic of monitors guarantees that at most one process will be accessing the buffer within a given time period. Note: **this mutual exclusion characteristic is implemented by the compiler, and programmers do not need to worry about it**);
5. **Condition variables** and **wait/wakeup operations** can be set in the monitor to solve synchronization problems. A process or thread can be made to wait on a condition variable (**in this case, the process should first release its right to use the monitor, that is, give up the "entry point"**); a process or thread waiting on a condition variable can be woken up through a wakeup operation.

## Monitor-like mechanisms in Java

In Java, if a function is described with the keyword synchronized, then that function can be called by only one thread within the same time period:

```java
static class monitor {
    private Item buffer[] = new Item[N];
    private int count = 0;
    
    public synchronized void insert(Item item) {
        /* ... */
    }
}
```

Only one thread can enter the `insert()` function at a time. If multiple threads call the `insert()` function at the same time, the later ones must queue up and wait.
